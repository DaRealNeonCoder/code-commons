Knowing the syntax of `def` is only the beginning. A useful function has one clear job, receives the values it needs, and returns a result instead of quietly changing unrelated state.

## Design a small interface

For a score report, separate the questions:

```python
def average(scores):
    return sum(scores) / len(scores)

def status(score):
    return "pass" if score >= 60 else "retry"
```

The caller does not need to know how each helper works. It can compose them:

```python
score = average([70, 80, 90])
print(status(score))
```

This is decomposition: turn one large problem into named steps that can be tested independently.

## Scope and side effects

Parameters and local variables belong to the function call. Prefer:

```python
def add_tax(price, rate):
    return price * (1 + rate)
```

over a function that reaches into a global `price` or prints when the caller needs to perform another calculation. Printing is useful at the edge of a program; returning values is more reusable inside it.

## Test the edges

Ask what should happen for an empty list, a zero value, a boundary score, or a missing key. Decide that behavior in the function contract. A short docstring or comment can state the decision before the implementation.

> [!TIP]
> If a function needs a paragraph of explanation, consider whether it is doing more than one job. Split the calculation from the input/output code first.
